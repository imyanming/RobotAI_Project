## 實驗一：手勢辨識準確率

**目的**
量化每個手勢類別的靜態辨識準確率，驗證 GestureEngine 的分類可靠性。

**方法**
1. 啟動 `python3 core/claude3.py`，切換至純手勢模式（按 V）
2. 每個手勢保持姿勢 1 秒，觀察 HUD 是否顯示對應指令
3. 每個手勢重複 **20 次**，記錄成功辨識次數
4. 環境：室內日光燈，操作者距鏡頭約 0.6 m
5. 每次測試之間回到握拳（SPACE）再換下一個手勢

**預期結果**
整體準確率 ≥ 90%；握拳與食指系列（W/S/A/D）應接近 100%；拇指系列（Q/E）可能略低（85–90%）

**記錄表格**

## 實驗二：系統延遲測量

**目的**
測量從手勢確認到機器人實際動作之間的端對端延遲，分別評估串流模式與純手勢模式的差異。

**方法**
1. 將手機架在旁邊，錄製 **MacBook 螢幕（HUD 指令切換瞬間）** 與 **機器人輪子轉動** 的同步影片（建議 120fps 以上）
2. 以慢動作回放，逐格計算兩個事件之間的幀數差，換算為毫秒
3. 重複 **10 次**，取平均值、最大值、最小值
4. 分別在兩種模式下各測一輪：
   - 模式 A：串流模式（show_stream = True）
   - 模式 B：純手勢模式（show_stream = False）

**預期結果**
- 總延遲 ≈ 100ms（確認幀）+ 80ms（safe_transition）+ <5ms（UDP）≈ 185ms
- 純手勢模式延遲略低（省去串流解碼 CPU 競爭）

## 實驗三：看門狗可靠性測試

**目的**
驗證 UDP 看門狗機制在通訊中斷時能於 0.5 秒內讓機器人停止，並確認重連後系統正常恢復。

**方法**
1. 操作機器人前進（W 指令鎖定）
2. **手動拔除樹莓派 WiFi**（或在路由器封鎖其 MAC）
3. 用碼表計時，從 WiFi 斷線到機器人停止的時間
4. 等待 3 秒後重新啟用 WiFi，確認：
   - 樹莓派重新連線
   - 重新做手勢後機器人正常反應
5. 重複 **5 次**，每次記錄停止時間與恢復狀態

**預期結果**
- 停止時間 < 500ms（watchdog timeout 設定值）
- 5 次測試全部成功停止
- 重連後系統完全恢復，不需重啟任何程序

## 實驗四：連續操作穩定性

**目的**
驗證系統在長時間連續操作下不出現當機、延遲累積、或馬達異常，確保系統可靠性滿足實際使用需求。

**方法**
1. 啟動所有服務，操作機器人在開放空間內連續行駛 **10 分鐘**
2. 操作路線建議：前進 → 後退 → 左移 → 右移 → 旋轉，循環操作
3. 每 2 分鐘紀錄一次觀察值
4. 觀察項目：
   - HUD 的 FPS 是否維持穩定
   - 指令是否出現明顯延遲
   - 馬達聲音是否異常（異響、過熱）
   - 程序是否崩潰或當機

**預期結果**
- FPS 維持 25+ 全程
- 無延遲累積（buffer 防堆積機制生效）
- 馬達正常運作，無異響
- 程序全程穩定，無例外或崩潰

## 實驗五：新使用者學習曲線

**目的**
評估系統對初次使用者的直觀性，測量上手時間並收集主觀使用體驗，用於論文 Usability 討論。

**方法**

**受試者準備**
- 招募 **3 名** 未使用過本系統的受試者
- 年齡、背景不限，建議涵蓋不同技術熟悉度
- 僅告知：「用手指數量控制機器人移動，握拳停止」，不透露詳細對應表

**測試流程**
1. 受試者自行探索 **5 分鐘**，不提供進一步提示
2. 記錄他們正確執行每個指令所需的時間
3. 5 分鐘後，給予完整手勢對照表，再操作 5 分鐘
4. 操作結束後填寫主觀評分問卷

**預期結果**
- 多數受試者在 2 分鐘內能掌握 W/S/A/D 四個基本移動
- 看到對照表後 Q/E 旋轉指令成功率提升至 90%+
- 主觀評分平均 ≥ 3.5 / 5
